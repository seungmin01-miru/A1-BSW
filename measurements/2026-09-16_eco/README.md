# 2026-09-16 eco (폴링 비용 절감) 1차 — 결과적으로 "SMT 짝 offline 만" 실험이 됨

## 의도
운용 부팅 `a1-bsw-rt-poll`(RT + idle=poll + intel_pstate=disable)에서 격리 코어의 폴링 전력을 줄이기 위해
(②) 격리 코어 클럭 800 MHz 고정 + (④) 격리 코어의 SMT 짝(CPU 9·11·13·15) offline 을 **동시에** 적용하고 30분 soak.

## 실제로 걸린 조건 (사후 확인 — 의도와 다름)
- `iso_pm.sh eco 800 smt-off` 가 **두 번 모두 SMT offline 까지만 하고 클럭 고정 전에 종료**했다(1차: `set -e` 아래 불필요한 조건식, 2차: offline 코어의 topology 디렉터리 부재). 사용자 실행 시점엔 오류가 화면에 드러나지 않았다.
- 따라서 soak 조건 = **CPU 9/11/13/15 offline, CPU 8/10/12/14 는 performance governor 800~2101 MHz 자유(사실상 2.1 GHz)**, cpuidle 없음, acpi-cpufreq. 격리 클럭 MSR 표본은 core_mhz.py 가 offline 코어에서 실패해 기록 없음(`- - -`).
- `power_sample.sh` 3회(rt-poll-idle, eco-idle ×2) **전부 출력 없이 종료** — `sensors` 미설치·cpuidle 디렉터리 없음·MSR 파이프 실패가 `set -e -o pipefail` 에 걸림. **전력 수치 없음.**
- 위 스크립트 결함 4건 + verify 의 offline 열 파싱 오류(IRQ 번호×4 가 "발생 횟수"로 찍힘) + CPU 라벨(스레드 순번→실제 CPU) 모두 이 세션에서 수정, 비루트 모의 실행으로 확인.

## 판정
- **SMT 짝을 hotplug 로 offline 하면 B 계열이 깨진다(A 계열로 복귀).** 클럭은 건드리지 않은 상태였으므로 이 결과는 ④ 단독 효과다. → **④(SMT 짝 offline) 기각.**
- 기전 가설(검증 안 됨): 커널이 offline 한 하드웨어 스레드는 `mwait` 로 **가장 깊은 C-state 에 재워 둔다**(play_dead). 즉 폴링 중인 스레드 바로 옆(같은 물리 코어)의 스레드가 진짜 C-state 에 들어간다. 이 조사 전체가 "하드웨어 스레드가 실제 C-state/유휴 경로에 들어가면 수백 µs 사건이 난다"는 방향이었고, 그것과 부합한다. 대안 설명(offline 코어의 nohz_full/RCU 정리 경로)도 배제 못 함. 운용 결정에는 필요 없음.
- BIOS 에서 HT 를 끄는 것은 hotplug 와 다른 경로(스레드 자체가 존재하지 않음)이므로 별도 사안이지만, BIOS 변경은 범위 밖이고 지금은 필요 없다.

## 다음 — ② 단독: 클럭 800 MHz 고정, SMT 유지
```bash
for c in 9 11 13 15; do echo 1 | sudo tee /sys/devices/system/cpu/cpu$c/online; done   # 상태 파일이 비어 있어 off 로는 안 돌아옴
cat /sys/devices/system/cpu/online                                                       # → 0-19
sudo bash tools/rt/power_sample.sh 60 rt-poll-idle                                       # 기준선(8스레드 2.1~2.5 GHz)
sudo bash tools/rt/iso_pm.sh eco 800                                                     # SMT 유지, 8-15 를 800 MHz 고정
bash tools/rt/iso_pm.sh status                                                           # 8~15 전부 performance 800~800 확인
sudo bash tools/rt/power_sample.sh 60 rt-poll-eco800-idle
bash tools/rt/a1_rt.sh verify
sudo bash tools/rt/a1_rt.sh soak 30
```
판정: 200 µs 초과 0·50 µs 초과 한 자리 → 운용 = rt-poll + `eco 800`(A-3 유닛에 포함) → 8시간. A 계열이면 ② 도 기각 → 폴링 비용은 부팅 옵션 비용으로 수용하고 PL1 조정(런타임 RAPL 65 W 시험)으로 방향 전환.

- **두 값이 정확히 PL1(35 W)이다.** 즉 이 부팅에서는 **부하가 전혀 없는 상태에서도 패키지가 전력 한도에 걸려 있다.** 20스레드가 전부 `performance` governor(=최대 클럭 요청) + `idle=poll` 로 폴링하므로 요구 전력이 35 W 를 넘고, RAPL 이 클럭을 깎아 정확히 35 W 에 맞춘다. OS 가 아니라 **하드웨어 전력 제한기가 클럭을 정하는 상태**다.
- eco 800 은 격리 코어에서 약 7~9 W(추정: 4 P-코어 × 3.2 GHz 폴링 ≈ 2 W/코어 → 0.8 GHz ≈ 0.4 W/코어)를 풀어 줬고, 그 예산을 **하우스키핑 코어가 곧바로 흡수**해 P 3.19 → 3.65 GHz, E 2.6 → 3.0 GHz 로 올라갔다. 그래서 패키지 합계는 그대로 35 W. 유휴 전력 절감 효과는 **0**, 대신 하우스키핑 클럭 여유가 +15 %.
- 이 표에서 격리 코어 단독 W 는 직접 측정이 아니다(RAPL 은 패키지·코어 합계만 제공). 위 7~9 W 는 클럭 이동량에서의 추정.

## 이 상태가 뜻하는 것
1. **유휴 = 항상 35 W, 45 °C.** 순정 generic 의 유휴(C6 수면, 수 W)와 달리 차량 대기 중에도 CPU 가 최대 허용 전력을 계속 태운다. 냉각은 감당하지만(스로틀 0) 전력·소음·수명 비용.
2. **인지 부하가 들어와도 클럭이 더 오를 여지가 없다.** 이미 PL1 이므로, 인지가 쓰는 만큼 폴링 클럭이 내려가 자리를 내준다(총량 고정). 격리 코어는 800 MHz 고정이라 더 내려갈 것이 없고 약 2 W 만 쓰므로, 인지 12스레드가 쓸 수 있는 예산 ≈ 33 W → 전 코어 지속 클럭 대략 P 3.0~3.3 / E 2.6 GHz 수준(추정, 2-1 에서 실측).
3. **RAPL 이 하우스키핑 클럭을 수시로 조정**한다 — 즉 acpi-cpufreq 로 OS 쪽 전이는 막았지만 하드웨어 전력 제한기의 전이는 남아 있다. 격리 코어를 800 MHz 로 박아 놓으면 RAPL 조정 대상에서 벗어나는데, eco 800 의 최악 67 µs(157 → 67)가 이것과 관련 있을 가능성(가설).

## schedutil — 실패 (클럭 안 내려감)
- `iso_pm.sh hk schedutil` 적용 후 60초: **35.0 W / 하우스키핑 3,653 MHz / cpu0 time_in_state 100 % 최대·전이 1회** → 한 번도 내리지 않음.
- 원인: schedutil 은 "RT 태스크가 실행 가능하면 최대 클럭" 규칙이 고정돼 있고, PREEMPT_RT 는 모든 IRQ 핸들러를 FIFO 스레드로 돌린다(irq/* 98개, RT 226개). 하우스키핑 12코어에 16,000 IRQ/s → 재평가마다 "RT 활동" → 항상 최대. RT 커널 + schedutil 은 유휴 클럭 하강이 불가능한 조합.
- 대안 B(`kernel.sched_util_clamp_min_rt_default=0`)는 전역 스케줄러 의미 변경이라 보류.

## ondemand — 성공
- `iso_pm.sh hk ondemand`(기본 튠: sampling 10 ms, up_threshold 95, io_is_busy 1). 유휴 60초: **패키지 14.2 W, 코어 4.1 W, 37 °C**, 하우스키핑 803~958 MHz, 격리 799 MHz. governor 변경 뒤 몇 분에 cpu0 1,406 / cpu16 3,379 회 전이 — 활발히 동작.

- **⑤ 채택 (ondemand). 운용 설정 최종 = `a1-bsw-rt-poll` 부팅 + `iso_pm.sh eco 800` + `iso_pm.sh hk ondemand`.** 전 실험 중 최선(50 µs 초과 0, 스레드별 최악 20~27 µs).
