## 한 줄 요약

- 원격은 **0x210 을 직접** 보낸다(우리와 같은 ID) → 원격과 자율(can_guard)은 **동시에 못 쓴다.** can_guard 시작 거부는 고장이 아니라 설계된 안전 동작.
- can_guard 송신 실패는 Kvaser 고장이 아니라 **우리 듣기 도구(미러)의 핸들 구성** 문제 → `single_handle=True` 로 해결(미러·lift_cmd).
- 정지 상태에서 can_guard → 0x210 → 차량 반응은 확인. **가속·주행·실제 제어기 경로는 미확인.**
- 주의: **auto 000 을 보내면 페일세이프 브레이크가 풀린다.** 종료는 auto off 없이 brake 100 유지 후 stop.sh.

---

## Q1. 원격을 켜기만 해도 can_guard 가 멈추는 이유는?

**고장이 아니라 can_guard 가 스스로 시작을 거부한 것.**
can_guard 는 시작 전 1초 동안 버스를 듣고, 다른 0x210 이 보이면 종료 코드 3 으로 끝난다(`safety/can_guard/can_guard.py:140-150`).
11-03 원격은 켜져 있기만 해도(조작 안 해도, 드라이브를 넣어도) 0x210 을 47 Hz 로 계속 보냈다(auto 111, 조향 0) → 2회 시도 모두 거부.

## Q2. 원격 시험에서 0x156/0x157 은 없고, 조향·가속·감속 모두 0x210 인가?

**우리가 연결한 버스 기준으로는 그렇다.**
- 15:56~16:33 녹화 내내 0x156/0x157 은 0 프레임.
- 원격 조향·가속·브레이크·후진 때 바뀐 명령은 전부 0x210. 차량은 0x200(조향각·브레이크 위치·auto)·0x201(바퀴 속도)로 응답.

단, "리모컨 자체가 0x210 을 만든다"까지는 미확인. CAN 프레임엔 송신자 정보가 없어서, 리모컨 → (무선) → 수신기가 0x210 으로 바꿔 내보낼 수도 있다(R1 수신기 위치 미답).
어느 쪽이든 **차량 제어기가 받는 건 원격이든 우리든 같은 0x210 이고, 차량은 구분 못 한다.**

## Q3. 0x210 이 뭐길래 둘이 같이 보내면 안 되나?

0x210 = `USER_control_command`, **차량 운전 명령**.

| 필드 | 의미 |
|---|---|
| 조향 명령 | 목표 조향각(°), raw 1 = 0.1° |
| 브레이크 명령 | 0~100 % |
| 가속 명령 | 0~100 % |
| auto 비트 3개(조/브/가) | 각 축을 이 명령대로 움직일지(1) 말지(0) |

CAN ID 는 "누가 보냈나"가 아니라 "무슨 메시지인가"다. 둘이 동시에 보내면:
- 차량은 가장 최근 것을 따르므로 몇십 ms 마다 원격 명령 ↔ 우리 명령이 번갈아 적용 → 어느 쪽대로도 못 움직인다.
- 같은 순간 송신을 시작하면 데이터가 다른 비트에서 충돌 → 에러프레임.

can_guard 는 원격 명령을 막을 수 없으므로 **자기가 시작을 포기**한다. 해결은 원격을 끄는 것뿐.

## Q4. 그럼 지금은 자율과 원격이 공존 불가능한가?

**현재 확인된 것 기준으로 동시 사용은 불가, 전환(원격 전원 OFF)만 가능.**

| 상황 | 가능 | 근거 |
|---|---|---|
| 원격만 | ✅ | 11-03 오후 원격 주행 |
| 원격 끄고 can_guard 만 | ✅ | 21:41~ 2단계 |
| 둘 다 켬 | ❌ | can_guard 시작 거부 2회 |

업체 답으로 바뀔 수 있는 것:
- **V21** 원격을 켠 채 0x210 송신을 멈추는 대기 모드가 있나 → 있으면 "자율 주행 + 원격 넘겨받기" 가능할 수도.
- **V22** 원격을 끄면 차량 버스 전체가 꺼지는 현상(오후 4회). 밤 21:41 은 정상 — 조건 차이 모름.

**가장 큰 문제: 비상 정지.** 지금 구조로는 자율 중 원격으로 끼어들어 세울 수 없다(켜는 순간 충돌).
기존 "원격 ID 가 낮아 중재에서 이김(0x156)" 전제는 **무효**. 대회 원격 E-stop 요구 여부를 업체·대회측에 확인(V21, R3, R6).
당장 정지 수단은 stop.sh / can_guard 종료(0x210 끊김 → 0.4 s 안 브레이크 8.2) + 물리 E-stop.

## Q5. 코드는 왜 고쳤나? Kvaser 문제인가, 듣는(listen) 쪽 문제인가?

**증상**: can_guard 송신 시작 즉시 `canWriteSync` 타임아웃, 에러프레임 ~350/s, 차량 프레임 끊김. Kvaser 단자를 바꿔도 같음.

**원인 — 우리 듣기 도구를 연 방식.** Kvaser 장치·차량 문제 아님.
같은 Kvaser 채널에 미러(듣기·녹화)와 can_guard(송신)가 같이 붙어 있었고, 미러가 python-can 기본값(핸들 2개) + 자기 송신 에코(`receive_own_messages=True`)로 열려 있으면 can_guard 송신이 깨졌다.

| 분리 시험 (1프레임씩) | 결과 |
|---|---|
| 핸들 1개 단독 송신 | 성공 |
| 미러(2핸들 + 에코) 옆에서 송신 | **실패** |
| 미러·송신 모두 single_handle | 성공 |
| 미러 에코 끔 | 성공 |

- listen-only(silent) 모드 자체가 원인이라는 증거는 없다(분리 시험에서 바꾼 건 핸들 수·에코뿐).
- 드라이버 내부에서 **왜** 깨지는지는 미증명. 가설: 10-07 에 넣은 `kvaser_compat.py` 패치로 TXACK 설정이 처음 실제로 켜지면서 2핸들과 엮였을 수 있다(추정).

**수정**
- `tools/kvaser/kvaser_mirror.py`: `single_handle=True` (523f6f7)
- `safety/can_guard/lift_cmd.py`: 같은 구성이 남아 있어 같은 수정 (171facc). 11-03 은 lift_cmd 를 `--channel` 없이 돌려서 피했다.

**listen-only 사용법**: 1단계(녹화만)는 미러 `--listen-only` 유지 → 2단계(can_guard 송신)는 미러를 `--listen-only` 없이 재시작.

## Q6. 지금 can_guard 로 제어기 값을 차량에 잘 보낼 수 있나?

**확인됨 (정지, 수정 후)**
- 송신 오류 0, 우리 0x210 이 버스·녹화에 나옴.
- auto 비트 000/010/110 → 0x200 에 30 ms 안 반영.
- 조향: ×0.1, 불감대 ±2°, 지연 0.2 s, 명령 ±150 → 정착 ±150(순간 ±153), 원격과 같음.
- 브레이크: 위치 = % ÷ 10, **약 82 % 에서 8.2 포화**, 거는 쪽 빠름(≤0.18 s)·푸는 쪽 느림.

**미확인**
- 실제 제어기 경로: `/control/target` → `a1_control_adapter` → can_guard 는 실차에서 안 돌림(11-03 명령은 lift_cmd 로 사람이 입력).
- 가속: 가속 한계 0 % 로 막고 시험 → 가속 명령·`acc_is_auto_command` 미확인.
- 단위 변환: 제어기는 m/s², 차량은 %. 어댑터 변환표는 잠정값 → 주행 T3·T4 로 맞춰야 함.
- 전진/후진: 0x210 에 방향 필드 없음(V20).
- 주행 중 동작·타이밍(can_guard `--no-rt` 로 돌렸음).

→ **비트 단위 송신은 OK, 제어기 출력이 의도한 가감속·조향이 되는지는 주행 시험에서.**

## Q7. 가상 시험으로 can_guard 구동을 확인할 수 없나?

이미 있다.

| 시험 | 확인하는 것 |
|---|---|
| `tools/track_day/rehearse_track.sh` (~1분 30초) | 제어기 대역 → 어댑터 → can_guard → vcan0 가짜 차량. 17항목(m/s²·타이어각→0x210 변환, 워치독, 제어기 kill → HOLDING → STOPPED, NaN 래치, 재연결) |
| `tools/kvaser/rehearse_kvaser.sh` (~40초) | CANlib 가상 채널. 다른 0x210 → 시작 거부, auto on → 조향 추종 |
| `safety/can_guard/test/` | 인코딩·클램프·상태머신 단위 시험 |

**한계**: `rehearse_kvaser.sh` [3]단계는 11-03 실패 구성(미러 normal + can_guard + lift_cmd)과 같은데 **가상 채널에선 통과**했다. 가상 채널엔 실제 CAN 컨트롤러·TXACK·에러프레임이 없어서 드라이버·하드웨어 문제는 못 잡는다.

보강안
1. `sil/vcan/fake_a1_vehicle.py` 를 11-03 실측으로 갱신(0.4 s 타임아웃 → 브레이크 8.2, auto 000 → 브레이크 해제, 82 % 포화, 불감대 ±2°).
2. 실물 벤치(HIL): 진짜 Kvaser Leaf ↔ 다른 CAN 장치(PEAK 등) + 120 Ω 로 미러+can_guard+lift_cmd 조합 사전 점검.

## Q8. 코드를 고쳤으니 앞으로 Kvaser 쪽 에러는 없나?

**보장 못 한다.** 고친 건 11-03 실패한 그 구성 하나.

남은 위험
1. 근본 원인 미증명 → 다른 조합(프로그램 추가, 미러 listen-only 상태로 송신, 라이브러리 버전 변경)에서 재발 가능.
2. `kvaser_compat.py` 는 python-can 4.6.1 ↔ CANlib 5.52 임시 패치 — 버전 바뀌면 동작 변화 가능.
3. 순서·상태 문제(11-03 에도 kv0 DOWN 으로 중단, 단자 이동).
4. **미러 + can_guard + lift_cmd 세 핸들 동시 조합은 실물 미확인** → 11-04 순위 1.

다행인 점: 송신이 실패해도 차량은 0x210 이 0.4 s 끊기면 브레이크 8.2 로 잡았다(제멋대로 가지 않음).
