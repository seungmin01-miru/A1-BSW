## 1. 주기 통일

### 1-1. 현재 주기

| 구성 요소 | 주기 | 바꿀 수 있나 | 타이머 |
|---|---|---|---|
| 차량 상태 0x200 / 0x201 | **21.0 ms**(47.6 Hz) | ❌ 차량 고정 | 차량 자체 |
| 차량의 0x210 반영 | 21 ms 틱으로 추정(auto 수락 지연이 2.2~21.7 ms 로 고르게 퍼짐) | ❌ | 차량 자체 |
| 원격조종 0x156 / 0x157 | 10 ms | ❌ | 원격 유닛 |
| GNSS/INS | 10 ms(100 Hz) | 설정 | 수신기 |
| 제어기 | 미정 | ✅ | **독립 타이머 ①** |
| 어댑터(공유메모리 기록) | 20 ms(50 Hz) | ✅ | **독립 타이머 ②** |
| can_guard(0x210 송신) | 20 ms | ✅ | **독립 타이머 ③** |
| 브리지 토픽 | 수신 즉시 | — | 이벤트 |

문제
- **같은 숫자로 맞춰도 타이머가 3개면 지연이 줄지 않는다.** 각 단계가 다음 틱을 기다리므로 단계마다 0~T 가 더해진다.
  SIL 실측 제어기→0x210: 최소 13.6 / 중앙값 23.7 / 최대 33.6 ms(이론 최악 약 42 ms, 비격리).
- **20 ms 와 21 ms 의 맥놀이.** 우리 20 ms 와 차량 21 ms 는 1/(50 − 47.62) ≈ **0.42 s 주기**로 위상이 한 바퀴 돈다.
  제어기가 보는 상태의 나이와 차량의 명령 반영 지연이 0.42 s 마다 0~21 ms 를 오간다.
  그 결과 조향 응답 식별 데이터에 주기적인 지터가 섞인다.

### 1-2. 제어주기 기준안에 대한 판단

**방향은 맞다.** 주기의 주인은 하나여야 하고, 우리가 정할 수 있는 것 중에서는 제어기가 주인이 되는 게 자연스럽다.
다만 "모두 제어주기와 같은 숫자로 맞추기"로 끝내면 안 된다. **제어기 타이머 하나만 남기고 나머지는 그 출력에 이벤트로
따라가게** 해야 효과가 있다. 아래 1단계가 그 방법이다.

더 나은 안이 하나 있다. 바꿀 수 없는 유일한 클럭인 **차량 0x200 수신**을 기준으로 삼는 것이다(아래 2단계).
이 방식이 이론상 최선이지만 차량이 명령을 읽는 위상을 먼저 실측해야 하므로, 1단계를 먼저 하고 트랙에서 측정한 뒤 고른다.

### 1-3. 1단계 — 제어주기 기준 + 하류 이벤트 구동 (트랙 전, 권장)

- [ ] **제어주기 = 20 ms(50 Hz)로 확정.**
  - 이보다 빠르면 새 상태가 없다(차량 상태가 21 ms 마다 갱신, 0x210 반영도 21 ms 틱).
  - 솔버가 무거우면 40 ms(25 Hz)도 허용한다. 30 ms 같은 어중간한 값은 피한다.
  - MPC 의 `step_dt`, 지연 tap(조향 무반응 175 ms ≈ 20 ms × 9), 단위 스텝당 변화율 한계를 전부 같은 dt 로 맞춘다.
- [ ] **어댑터: 수신 즉시 기록.** `/control/target` 콜백에서 바로 공유메모리에 쓴다.
  - 50 Hz 타이머는 keepalive 로만 남긴다(새 입력이 없을 때 같은 값을 다시 써서 can_guard 워치독 유지).
  - 위치: `ros2_ws/src/a1_control_adapter/a1_control_adapter/cmd_adapter.py`.
- [ ] **can_guard: 새 명령이면 즉시 송신.** 주기 대기 중 공유메모리 seq 가 바뀌면 바로 0x210 을 보낸다.
  - 새 명령이 없으면 20 ms keepalive 송신.
  - 최소 송신 간격을 10 ms 로 제한한다. 10-07 재연결 때처럼 0x210 이 몰려 나가는 것을 막기 위해서다.
  - 안전 핵심 코드라 상태머신·한계 로직은 그대로 두고 송신 시점만 바꾼다. 유닛테스트, `rehearse_lift_guard.sh`,
    `rehearse_track.sh`, 8 h soak 를 다시 돌린다.
  - 위치: `safety/can_guard/can_guard.py` 메인 루프.
- [ ] **효과 측정.** `measure_latency.py` 로 전후를 비교한다. 기대: 제어기→0x210 수 ms 이내(격리 코어).
- [ ] **타임스탬프 기준으로 계산.** 제어기는 상태 메시지의 `header.stamp` 로 상태 나이를 계산한다. 명목 주기를 가정하지 않는다.

### 1-4. 2단계 — 차량 0x200 수신 기준 (트랙 측정 뒤 결정)

구조: 0x200 수신 → 제어 계산 → 즉시 송신. 클럭이 차량 하나뿐이라 맥놀이가 없다. 상태 나이도 항상 최소(수신 지연 + 계산 시간)가 된다.

- [ ] **트랙 측정(정지 상태).** 0x200 을 받은 뒤 0x210 을 보내는 시점을 0~20 ms 로 바꿔 가며 auto 비트·조향 반응 지연을 잰다.
  이 측정으로 차량이 0x210 을 읽는 위상을 찾는다.
- [ ] 위상이 분명하면 2단계로 전환한다. 제어기는 0x200 에 이벤트로 구동된다(GNSS 는 최신값 사용).
  - 0x200 이 끊기면 내부 20 ms 타이머로 대체한다.
  - 0x200 이 끊겼다는 사실은 can_guard 에도 알린다.
- 하지 않을 것: 0x210 을 21 ms 타이머로 따로 돌리기. 숫자가 같아도 발진기가 달라 결국 위상이 흐른다.
