## 1. 이 컴포넌트가 왜 필요한가

안전 MCU 하드웨어를 이번 대회에서는 두지 않기로 했다(§7.4 잔여 위험 수용). 그 대신 **메인 PC 위의 별도 프로세스**가 MCU의 역할 일부를 대신한다 — 제어 노드가 죽거나, 인지가 죽거나, ROS2/DDS 가 지연돼도 차량으로 나가는 CAN 신호(조향·가감속)만은 계속 안전하게 관리한다는 게 목표다.

```
[ROS2 제어 노드]──공유메모리(seqlock)──▶ [can_guard] ──0x156/0x157──▶ [EAIT DBW 컨트롤러]──▶ 액추에이터
   (MPC/판단, 아직 없음)                     │        ▲
[인지 프로세스]────공유메모리(seqlock)────────┘        └──0x711 VS(신규)── 같은 CAN 버스에서 직접 읽음
   (아직 없음)                            상태머신: INIT→ACTIVE→HOLDING/DEGRADED→STOPPED
                                          최종 백업: 차량 측 벤더 AEB (0x156 무신호 ≥1000ms)
```

**설계 원칙(§7.2)**: `can_guard` 는 ROS2/DDS 를 아예 안 쓴다(별도 프로세스, `ros2_ws/` 밖). Phase C 조사에서 ROS2/DDS 슬라이스는 A-3 레시피(격리 코어+SCHED_FIFO)를 적용해도 1~2ms 지연이 그대로였던 반면, `can_guard` 처럼 raw SocketCAN 만 쓰면 같은 레시피로 수십 µs 대까지 내려간다 — 그래서 안전 임계 경로를 ROS2 밖에 둔다.

### 2.5 DEGRADED/STOPPED 정책 — 초안 완료 (2026-09-21, 팀 확인 대기)

체크리스트 §7.2 원문("perception-process death is a safety event ... decel per team policy")을 근거로 잠정 초안을 코드로 만들었다. **미정 항목이 아니라 "검토 대기 중인 기본값"** 상태다.

- **DEGRADED**(인지 하트비트 끊김): 기존엔 ACTIVE와 동일하게 명령을 그대로 통과시켰는데, 이제 **HOLDING과 같은 방식**(조향 얼림 + 가감속 0 램프)으로 바꿨다. 명령이 계속 살아있어도 DEGRADED가 2초(잠정값) 넘게 지속되면 STOPPED로 직접 전이한다 — "인지 없이 명령을 무한정 신뢰하지 않는다"는 원칙을 실제로 강제.
- **STOPPED 속도 수렴**: 지금까지는 "HOLDING 지속시간"만으로 시간 기반 근사를 했는데, 이제 `can_guard`가 이미 열어둔 CAN 버스로 0x711(VS, 실측 차속)을 직접 읽어(새 프로세스·새 IPC 채널 없이) 판단한다. HOLDING/DEGRADED → STOPPED는 "지속시간 상한" **또는** "실측 차속이 정지 문턱(3km/h, 잠정값) 이하" 중 먼저 오는 쪽. 차속 정보가 없거나 오래됐으면 기존 시간 기반으로 자동 복귀. **정상 주행(ACTIVE) 중에는 차속을 절대 참조하지 않는다** — 서행·정차를 정지로 오판하지 않도록.
- 라이브 vcan0로 두 경로(시간 기반 전이, 차속 기반 조기 전이) 모두 직접 확인, 유닛테스트 13개 추가(51→64), P-1/P-2 재실행 회귀 없음.

### 2.6 그 과정에서 발견·수정한 버그 6건

개발·측정 과정에서 실제로 재현·수정한 버그: (1) ctypes 버퍼 익스포트로 인한 `close()` 실패, (2) seqlock 재시도 횟수 부족, (3) 시험 스크립트의 자원 유출(`try` 밖 리소스 생성), (4) 커스텀 tracker 경고, (5) **SIGTERM이 Python 기본 처리라 `finally`를 안 태워 `/dev/shm`이 실제로 누수됨** — 지금까지 전체 SIL 시험이 이 문제를 안고 있었다, (6) **`wait_for_shm`이 cmd 세그먼트만 확인하고 hb 세그먼트를 안 기다려 인지 프로세스가 경합 조건으로 즉사** — 첫 8시간 시도가 이 때문에 20초 만에 허위 종료됨. 전부 재현·수정·재검증 완료. 상세는 `safety/can_guard/README.md`.

## 3. 앞으로 필요한 것

**결론부터**: `can_guard` 자체(뼈대)는 설계·구현·검증이 끝났다. 남은 일은 "숫자만 넣으면 되는 것"이 아니라 **네 가지 성격이 다른 작업**으로 나뉜다.

### 3.1 숫자만 넣으면 되는 것 — 1개

| 항목 | 현재 상태 | 필요한 것 |
|---|---|---|
| 변화율 상한 (`eps_cmd` deg/s, `acc_cmd` jerk) | 의도적으로 무제한(추측해서 안 채움) | 실차 액추에이터 스펙(`can_status_parameters_full.md`, 저장소에 없음) → CLI 인자로 바로 반영 가능, 코드 변경 불필요 |

### 3.2 팀이 정책을 확정해야 하는 것 — 3개 (지금은 잠정 기본값으로 동작 중)

| 항목 | 지금 기본값(초안) | 결정할 것 |
|---|---|---|
| DEGRADED 감속 목표 | 가감속을 0으로 램프(코스팅) | 실제 제동(음수 목표)을 원하는지, 원한다면 목표 감속도 얼마인지 |
| DEGRADED 지속 상한 | 2.0초 | 이 값이 적절한지 |
| STOPPED 정지 판정 문턱 | 실측 차속 3km/h 이하 | 이 값이 적절한지 |
| 0x157에 `Alive_Cnt`가 없는 이유 | 미확인 | EAIT 팀에 직접 확인 필요(코드 문제 아님) |

### 3.3 can_guard 밖에서 새로 만들어야 하는 것 — 가장 큰 덩어리

지금까지 모든 시험(P-1/P-2/A-3/8시간)은 `fake_control_node.py`/`fake_perception.py`(사인파 흉내)로 진행했다. **진짜 ROS2 제어 노드와 진짜 인지 프로세스 자체가 아직 개발되지 않았다.**

- `can_guard` 쪽은 이미 준비돼 있다 — 제어 노드가 `CommandChannel.open()`, 인지 프로세스가 `HeartbeatChannel.open()`만 부르면 바로 연결된다.
- 이건 "연결 작업"이 아니라 **MPC/판단 로직을 가진 제어 노드, 인지 결과를 하트비트로 내보내는 프로세스를 새로 개발**하는, `can_guard`보다 훨씬 큰 작업이다.

### 3.4 배포 단계

- `can_guard.service`(systemd 유닛) — 초안은 있으나 미설치. 진짜 제어 노드 없이 상시 기동하는 건 이르다고 판단해 보류 중.

| P-3/P-4 (guard 자체 kill/hang, 재시작 시간) | systemd 설치 후 |

| P-10/P-11 (콜드부트/재시작 시간) | 실 하드웨어 |

### 3.6 즉시 처리 가능한 후속 작업

- **A-3 재검증**: DEGRADED/STOPPED 초안에서 메인 루프에 `bus.recv()`가 하나 추가됐다. 비-RT 환경에서 훑어본 결과는 이상 없었지만(1000주기 최대 144µs), 표준 절차상 실조건(격리 코어+RT 우선순위)에서 다시 재봐야 한다 — `sudo chrt` 필요, 사용자 직접 실행.
