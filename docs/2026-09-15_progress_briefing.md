## 1. BSW(Basic Software) 범위 — 이 프로젝트가 책임지는 것

```
[센서·인지(별도 팀)] ──작은 결과값만──▶ [BSW: 메인 PC 위 실시간 CAN 스택] ──0x156/0x157──▶ [EAIT DBW 컨트롤러] ──▶ 액추에이터
                                              ▲                                                    │
                                              └───────── 0x710~0x713 (EPS/ACC/휠속/IMU 상태) ◀──────┘
```

| 포함 | 제외 |
|---|---|
| RT 커널·격리 코어 튜닝, 실시간 예산 실측 | 인지 알고리즘(LiDAR/카메라/localization) |
| CAN 인터페이스(vcan0 SIL → PEAK can0 실차) | 제어 정책 NN 자체(⚠️ 모델 미선정) |
| DBC 기반 인코더/디코더, ROS2 브리지 | 안전 MCU 하드웨어(**대회에서는 보류**, PC 전용 안전층으로 대체) |
| E2E(alive counter) 체크, 헬스 슈퍼바이저, `can_guard`(명령 중재·워치독) | 차량 측 fail-safe(EAIT 벤더 내장, 0x156 1 s 두절 → AEB) |

**실시간 요구**: 제어 10 ms 주기, 0x156 TX 10 ms, 차량 타임아웃 1000 ms. §7 원안 목표 "최악 수십~100 µs" → **재정의 제안 D4: 최악 1 ms, 99.99 % 100 µs**.

## 3. Phase A — 무엇을 확인했고 무엇을 알아냈나 (9/12~9/15)

### 3.1 커널 결정
- 기존 5.15-rt 폐기(WiFi 드라이버 부재 + NVIDIA 470 RT 빌드 거부) → **`6.8.1-1059-realtime`**(Ubuntu Pro 22.04 백포트) 채택. NVIDIA는 공식 미지원이라 우회 빌드(잠재 결함 1건 관측, 정상 운용 8 h 동안 0회).
- 대조군(generic + `preempt=full`, 같은 격리 튜닝)은 RT보다 뚜렷이 나쁨(50 µs 초과 사건 10배) → **D1 = RT 유지** (단, 전원관리 고정 후 재비교 예정 = 1-1b).

### 3.2 실측 결과 (격리 코어 8–15, GPU 80 % + CPU·메모리·I/O 합성 최악 부하)

| 조건 | 시간 | 최악 | 50 µs 초과 | 판정 |
|---|---|---|---|---|
| RT + 격리 튜닝 (A) | 30 min | 467 µs | 102 | 조건부 |
| RT + 격리 튜닝 (A) | **8 h** | 828 µs | 3,593 (400 µs 초과 231) | **1 ms 초과 0** — D4 예산 충족 |
| generic + 격리 + preempt=full | 30 min | 935 µs | 1,072 | RT보다 나쁨 |
| **RT + 전원관리 전역 차단 (B)** | 30 min | **43 µs** | **0** | 원인 확정 |
| RT + 격리 코어만 전원관리 차단 (C/C2) | 30 min | 995 / 899 µs | 3,203 / 204 | 실패 → 원인은 격리 코어 밖 |
| RT + **전 코어** 클럭 고정, 런타임 (C3) | 30 min | 837 µs | 216 | 실패 → 런타임 설정으로는 부족, 부팅 시점 요인(HWP 자체/유휴 경로) |

### 3.3 원인 규명의 결론
1. 격리 코어에 **장치 인터럽트 0건**, IPI는 균등 — 소프트웨어 유입 아님.
2. ftrace 포착: 스파이크 순간 **8코어가 동시에** 늦게 깸 → 패키지(칩) 단위 사건.
3. 전원관리를 전부 끄면(B) 사건 **0** → 원인 = **CPU 절전·클럭 전이**.
4. 격리 코어만 고정(C2)해도 남음 → **하우스키핑 코어의 클럭 전이가 패키지 공용 자원(전압/전력 제어, PL1 = 35 W)을 흔들어 전 코어를 멈춤.** `isolcpus`로는 못 막음.
5. "코어 6 결함" 가설은 기각(전원관리 끄니 다른 코어와 동일).

### 3.4 운용 설정 — 현재 상태 (C3 이후)
- **확정된 사실**: 부팅 시 `idle=poll intel_pstate=disable max_cstate=0`(B)이면 최악 43 µs, 50 µs 초과 0.
- **런타임 조정(격리만/전 코어 클럭 고정, C~C3)으로는 재현 실패** → 원인은 부팅 때만 바꿀 수 있는 요인: **HWP(하드웨어 자율 전원관리)가 켜져 있는 것** 또는 **유휴 루프 경로**.
- **다음(1-6e)**: B를 두 조각으로 나눠 각각 부팅·30분 — B1 = HWP만 끔, B2 = 유휴 폴링만. 이긴 쪽이 운용 설정.
- 결과가 나올 때까지의 **안전한 선택지**: ① B 그대로 사용(비용: 전 코어 상시 폴링·터보 없음, 패키지 +3~4 °C) ② 기본 튜닝으로 **최악 1 ms 수용**(8 h 실측: 1 ms 초과 0, 10분 주행당 0.4~0.8 ms 사건 ~1.4회).

## 4. Phase B — vcan SIL 환경 (완료)
- `vcan0` 부팅 자동 생성(systemd), `cansend→candump` 왕복 ✅
- 실제 DBC로 0x712 `EAIT_INFO_SPD` 10 ms 송신 → 디코드: **100.0 Hz**, 휠속 4개 물리값 일치, 카운터 건너뜀 0
- 0x156 `EAIT_Control_01` 인코딩 바이트 검증(`--set` 신호 지정)
- 송신 주기 편차: 비격리 61/88 µs → 격리 코어 + 타이머 여유 1 µs + SCHED_FIFO **5/9 µs** → Phase C 노드의 실행 레시피 확정
- DBC 사실: 주기 속성 없음(스펙표 내장), `Turn_Signal` 2=좌/4=우, KIAPI 0x124~0x129 신호 0개, 0x156 카운터명 `Aliv_Cnt`(오타), `AEB_decel_value` 0x00→1.0 G 특례
